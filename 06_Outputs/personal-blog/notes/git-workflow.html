Mac 本地开发 - 服务器测试 - GitHub 协作工程指南

定义本地开发、远端验证和多人协作之间的责任边界与闭环。

Mac 本地开发 - 服务器测试 - GitHub 协作工程指南

本文档定义一套适用于“本地使用 AI coding agent 开发，服务器/HPC 负责测试训练，GitHub 负责多人协作与版本管理”的工程工作流。

适用场景：

  • 开发者在本地 Mac 上可以顺畅使用 Claude、GPT、Cursor、Codex、Aider 等 AI coding agent；
  • 服务器/HPC 具备训练、GPU、数据或特殊运行环境，但不适合运行 AI agent；
  • 团队通过 GitHub 协作开发；
  • 部分代码必须经过服务器测试、训练或 benchmark 后才能合入团队分支。

核心原则：

本地 Mac 是开发工作台，GitHub 是代码事实源，服务器是实验与验证环境。

1. 整体架构

┌──────────────────────────┐
        │        Mac 本地           │
        │ AI agent / IDE / 小测试   │
        └────────────┬─────────────┘
                     │ push / PR
                     ▼
        ┌──────────────────────────┐
        │        个人 GitHub        │
        │ fork / feature 分支       │
        └────────────┬─────────────┘
                     │ pull / fetch
                     ▼
        ┌──────────────────────────┐
        │       服务器 / HPC        │
        │ smoke test / train / eval │
        └────────────┬─────────────┘
                     │ 日志 / 指标 / 报告
                     ▼
        ┌──────────────────────────┐
        │        公用 GitHub        │
        │ PR → dev → main           │
        └──────────────────────────┘

推荐闭环：

本地开发 → 本地测试 → push 到个人分支 → 服务器拉取测试 → 回传日志 → 修复 → PR 到公用 dev

2. 角色分工

2.1 本地 Mac

本地负责：

  • AI agent 辅助编码；
  • 阅读、重构、生成测试；
  • 运行轻量单元测试；
  • 提交 Git commit；
  • 发起 Pull Request；
  • 分析服务器日志并修复代码。

本地不负责：

  • 长期保存大数据集；
  • 保存大模型权重；
  • 运行高资源训练任务；
  • 作为团队唯一代码源。

2.2 GitHub

GitHub 负责：

  • 保存代码版本；
  • 管理多人协作；
  • 管理分支；
  • 管理 Pull Request；
  • 触发 CI；
  • 保存小型报告、测试日志摘要和文档。

GitHub 不应保存：

  • 大型数据集；
  • 模型权重；
  • 训练输出；
  • 个人密钥；
  • .env 文件；
  • 服务器私有路径中的临时文件。

2.3 服务器 / HPC

服务器负责：

  • GPU 训练；
  • 大规模测试；
  • benchmark；
  • 数据集访问；
  • 复现实验；
  • 生成运行日志与实验报告。

服务器不负责：

  • 主要代码开发；
  • AI agent 交互式编码；
  • 保存未提交的重要代码修改；
  • 直接向公用 dev 分支推送未经审查代码。

3. GitHub 仓库关系

推荐使用两个远端：

origin   = 个人 GitHub 仓库 / fork
        upstream = 团队公用 GitHub 仓库

示例：

git remote -v

应类似：

origin    git@github.com:yourname/project.git
        upstream  git@github.com:team/project.git

如果还没有设置 upstream：

git remote add upstream git@github.com:team/project.git

4. 分支策略

推荐分支模型：

main                 稳定版本分支
        dev                  团队开发集成分支
        feature/xxx          个人功能分支
        fix/xxx              bug 修复分支
        exp/xxx              实验性分支

4.1 main

main 是稳定分支，只合入经过充分验证的版本。

规则：

  • 不直接 push；
  • 只通过 PR 合并；
  • 必须通过 CI；
  • 必须经过 review。

4.2 dev

dev 是团队开发集成分支。

规则：

  • 个人功能完成后向 dev 发 PR；
  • 不建议直接 push；
  • 合入前至少完成本地测试；
  • 涉及训练、推理、数据处理的代码，应完成服务器 smoke test。

4.3 feature 分支

每个功能一个分支，例如：

git checkout -b feature/memory-module

命名建议：

feature/add-memory-module
        feature/refactor-audio-pipeline
        fix/server-config-path
        exp/new-training-loss

推荐结构：

6. .gitignore 规范

项目根目录必须有 .gitignore。

推荐内容：

# Python
        __pycache__/
        *.py[cod]
        .pytest_cache/
        .mypy_cache/
        .ruff_cache/

        # Virtual environments
        .venv/
        venv/
        env/

        # Jupyter
        .ipynb_checkpoints/

        # Data and outputs
        data/
        datasets/
        outputs/
        runs/
        logs/
        checkpoints/
        wandb/

        # Model files
        *.pt
        *.pth
        *.ckpt
        *.onnx
        *.npz
        *.h5

        # Environment variables / secrets
        .env
        .env.local
        *.key
        *.pem

        # OS / editor
        .DS_Store
        .vscode/
        .idea/

注意：

如果某个文件已经被 Git 跟踪，再加入 .gitignore 不会自动停止跟踪。需要执行：

git rm --cached path/to/file

如果是整个目录：

git rm -r --cached data/

7. 本地开发流程

7.1 同步团队最新代码

git fetch upstream
        git checkout dev
        git pull --ff-only upstream dev

7.2 新建功能分支

git checkout -b feature/xxx

7.3 使用 AI agent 开发

推荐给 agent 的提示词：

你是本项目的 coding agent。请先不要修改代码。
        请阅读 README、src/、tests/、configs/ 中与任务相关的文件。

        目标：实现 XXX。

        约束：
        1. 保持现有 API 兼容；
        2. 不要引入大型依赖；
        3. 必须补充或更新测试；
        4. 修改前先输出计划；
        5. 修改后运行 harness/run_local_checks.sh；
        6. 不要改动 data、outputs、checkpoints、.env 等文件。

开发原则：

小步修改 → 本地测试 → agent 自审 → 人类检查 → commit

不要让 agent 一次性大范围重写整个项目。

8. 本地测试 harness

项目应提供统一测试入口：

bash harness/run_local_checks.sh

示例：

#!/usr/bin/env bash
        set -euo pipefail

        echo "[1/5] format"
        ruff format .

        echo "[2/5] lint"
        ruff check .

        echo "[3/5] type check"
        mypy src || true

        echo "[4/5] unit tests"
        pytest tests -q

        echo "[5/5] smoke test"
        python scripts/smoke_test.py --config configs/local.yaml

如果项目不是 Python，可替换为对应语言的检查命令。

原则：

  • 本地 harness 必须轻量；
  • 可以在几分钟内跑完；
  • 不依赖大数据；
  • 不依赖 GPU；
  • 必须能被 AI agent 调用和理解。

9. 提交到个人 GitHub

完成本地修改和测试后：

git status
        git add .
        git commit -m "feat: add xxx"
        git push -u origin feature/xxx

提交信息建议：

feat: add memory storage interface
        fix: resolve server config path
        refactor: simplify audio pipeline
        chore: update gitignore
        test: add smoke test for training loop
        docs: add server usage guide

10. 服务器测试流程

10.1 首次克隆项目

服务器上：

mkdir -p ~/projects
        cd ~/projects
        git clone git@github.com:yourname/project.git
        cd project

如需同时访问团队仓库：

git remote add upstream git@github.com:team/project.git

10.2 拉取个人功能分支

cd ~/projects/project
        git fetch origin
        git checkout feature/xxx
        git pull --ff-only origin feature/xxx

如果分支不存在：

git checkout -b feature/xxx origin/feature/xxx

10.3 运行服务器 smoke test

统一入口：

bash harness/run_server_smoke.sh

推荐写法：

#!/usr/bin/env bash
        set -euo pipefail

        echo "[server] host"
        hostname

        echo "[server] date"
        date

        echo "[server] GPU"
        nvidia-smi || true

        echo "[server] python"
        python -V

        echo "[server] smoke train"
        python scripts/train.py \
          --config configs/server.yaml \
          --max-steps 20 \
          --output-dir outputs/smoke_$(date +%Y%m%d_%H%M%S)

        echo "[server] smoke eval"
        python scripts/eval.py \
          --config configs/server.yaml \
          --latest-output outputs

保存日志：

mkdir -p reports
        bash harness/run_server_smoke.sh 2>&1 | tee reports/server_smoke_$(date +%Y%m%d_%H%M%S).log

11. 服务器与本地之间传输日志

从本地 Mac 拉取服务器日志：

scp xiaoyu.xing@server:~/projects/project/reports/server_smoke_*.log ./reports/

也可以只拉取最新日志：

scp xiaoyu.xing@server:~/projects/project/reports/server_smoke_20260508_120000.log ./reports/

然后把日志交给本地 AI agent 分析：

这是服务器 smoke test 日志。请判断：
        1. 是否通过；
        2. 如果失败，根因是什么；
        3. 应该修改代码、配置还是服务器环境；
        4. 给出最小修复方案；
        5. 修复后需要补充哪些测试。

12. 临时同步：rsync

推荐主路径是 Git：

本地 commit → push GitHub → 服务器 pull

但在高频调试阶段，可以临时用 rsync。

示例脚本：

#!/usr/bin/env bash
        set -euo pipefail

        SERVER="xiaoyu.xing@server"
        REMOTE_DIR="/path/to/server/project"

        rsync -avz --delete \
          --exclude ".git" \
          --exclude ".venv" \
          --exclude "__pycache__" \
          --exclude ".pytest_cache" \
          --exclude ".mypy_cache" \
          --exclude ".ruff_cache" \
          --exclude "outputs" \
          --exclude "runs" \
          --exclude "checkpoints" \
          --exclude "data" \
          ./ "$SERVER:$REMOTE_DIR/"

注意：

  • rsync 只用于临时调试；
  • 最终合并必须通过 Git commit 和 PR；
  • 不要用 rsync 覆盖服务器上的数据集和实验结果。

PR 方向：

14. AI agent 审查流程

在发 PR 前，让 AI agent 以 reviewer 身份审查。

推荐提示词：

你现在不是实现者，而是代码审查员。

        请审查当前分支相对 dev 的 diff：
        1. 是否有明显 bug；
        2. 是否破坏现有 API；
        3. 是否缺少测试；
        4. 是否有路径硬编码；
        5. 是否有随机性不可复现问题；
        6. 是否有大文件、密钥、token、实验输出误提交；
        7. 是否有服务器环境不兼容问题。

        请按照：
        - Blocker
        - Major
        - Minor
        - Suggested tests
        输出。
        不要直接修改代码，先给 review。

生成 diff：

git fetch upstream
        git diff upstream/dev...HEAD

15. GitHub Actions CI

如果项目支持自动 CI，可以添加：

name: CI

        on:
          pull_request:
          push:
            branches: [main, dev]

        jobs:
          local-checks:
            runs-on: ubuntu-latest

            steps:
              - uses: actions/checkout@v4

              - name: Set up Python
                uses: actions/setup-python@v5
                with:
                  python-version: "3.11"

              - name: Install dependencies
                run: |
                  python -m pip install -U pip
                  pip install -e ".[dev]"

              - name: Run local harness
                run: |
                  bash harness/run_local_checks.sh

CI 只做轻量测试，不跑大规模训练。

大规模训练仍放在服务器上执行。

16. 大文件与实验产物管理

不要提交：

data/
        datasets/
        outputs/
        runs/
        checkpoints/
        wandb/
        *.pt
        *.pth
        *.ckpt
        *.onnx
        *.npz
        *.h5

推荐服务器目录：

~/datasets/project_name/
        ~/runs/project_name/
        ~/checkpoints/project_name/

代码通过配置文件引用这些路径：

data_root: /server/path/datasets/project_name
        output_root: /server/path/runs/project_name

不要把服务器绝对路径硬编码进源码。

17. 配置文件规范

至少维护两套配置：

configs/local.yaml
        configs/server.yaml

local.yaml

data_root: ./data/small
        output_root: ./outputs/local
        max_steps: 10
        batch_size: 2
        device: cpu

server.yaml

data_root: /server/path/datasets/project_name
        output_root: /server/path/runs/project_name
        max_steps: 10000
        batch_size: 32
        device: cuda

原则：

  • 本地配置轻量；
  • 服务器配置完整；
  • 路径写在配置里，不写死在代码里；
  • 配置文件可以被命令行覆盖。

18. 服务器环境文档 SERVER.md

每个项目建议写 SERVER.md。

模板：

# Server Guide

        ## Server

        Host: xxx
        Project path: ~/projects/project
        Data path: /path/to/dataset
        Output path: /path/to/runs

        ## Update code

git fetch origin git checkout <branch> git pull --ff-only origin <branch>


        ## Run smoke test

bash harness/run_server_smoke.sh


        ## Run training

python scripts/train.py --config configs/server.yaml


        ## Collect logs

scp user@server:~/projects/project/reports/*.log ./reports/


        ## Notes

        - Do not edit source code directly on server unless necessary.
        - Do not commit data, checkpoints, or outputs.
        - Keep server-specific paths in configs/server.yaml.

20. 常见问题与处理

20.1 服务器上能不能直接改代码？

可以临时改，但不推荐。

如果必须改：

git diff > server_debug.patch

然后把 patch 拉回本地：

scp server:~/projects/project/server_debug.patch .
        git apply server_debug.patch

最终仍在本地 commit 和 push。

20.2 服务器上有未提交修改，无法 pull 怎么办？

先看：

git status
        git diff

如果是不需要的临时修改：

git restore .

如果要保留：

git stash push -m "server temporary changes"
        git pull --ff-only

20.3 本地和服务器环境不一致怎么办？

把差异写进：

configs/local.yaml
        configs/server.yaml
        SERVER.md

不要写死在源码中。

20.4 测试通过但 PR 冲突怎么办？

本地同步 dev：

git fetch upstream
        git checkout feature/xxx
        git merge upstream/dev

解决冲突后：

bash harness/run_local_checks.sh
        git push

如有必要，重新跑服务器 smoke test。

20.5 什么时候可以合并到 dev？

至少满足：

本地 harness 通过
        PR 描述清楚
        没有大文件和密钥
        关键功能有测试
        必要时服务器 smoke test 通过
        至少一名队友 review

21. 最小落地清单

一个新项目最少需要准备：

.gitignore
        README.md
        SERVER.md
        configs/local.yaml
        configs/server.yaml
        harness/run_local_checks.sh
        harness/run_server_smoke.sh
        .github/pull_request_template.md

团队只要遵循这套流程，就可以做到：

  • 本地 AI agent 高效开发；
  • GitHub 可审查、可回滚；
  • 服务器测试可复现；
  • 大文件不污染仓库；
  • 新成员能快速上手；
  • 公用 dev 分支保持相对稳定。

22. 最终原则

1. 代码进 GitHub。
        2. 大数据和模型不进 GitHub。
        3. 本地负责开发，服务器负责验证。
        4. 个人分支通过测试后再 PR 到公用 dev。
        5. 不直接向公用 dev 推送未经审查代码。
        6. AI agent 可以写代码，但必须经过 harness 和人类 review。
        7. 所有服务器操作都尽量脚本化、文档化、可复现。

一句话总结：

Mac 是开发工作台，GitHub 是协作事实源，服务器是实验工厂，harness 是三者之间的标准接口。
