Project Note

长期记忆系统

为语音 Agent 设计跨会话记忆：用户画像、偏好、项目状态、显式记忆、检索注入与调试 API。

下面给出一个 xtalk-memory 模块设计思路。它不是简单加一个 memory.py，而是把 memory 做成一个符合 X-Talk 原有架构的 事件驱动、可插拔、低延迟、可长期演化的 Agent Memory 子系统。

我的总体判断是：

X-Talk 现在已经有 Memory 的“基础构件”：
        - Chat History / Context
        - Embedding Search
        - Local Search / Document RAG
        - Agent Tool 机制
        - Speaker Recognition
        - EventBus + Manager + Pipeline 扩展机制

        但还没有一个完整的 Long-term Memory / Self-evolving Memory 模块：
        - 没有长期用户画像
        - 没有跨会话记忆存储
        - 没有自动记忆抽取
        - 没有记忆去重、冲突、遗忘、置信度管理
        - 没有反思式 self-evolution 闭环

X-Talk 文档目前的 Text Embedding 更像“上传文档后的检索增强”，通过 OpenAIEmbeddings 和 xtalk_instance.embed_text(session_id=session_id, text=text) 把文本加入检索流程。([X-Talk][1]) 但 Service Configuration 又说明 embedding 数据位于 <data_dir>/sessions/<session_id>/embeddings，并且 session 目录会在 shutdown 时删除。([X-Talk][2]) 所以它不是严格意义上的长期记忆。

1. xtalk-memory 的定位

我建议把 xtalk-memory 定位为：

一个面向 X-Talk 语音 Agent 的长期记忆与自进化子系统，
        负责从多轮语音交互中抽取、组织、更新、检索和遗忘用户相关记忆，
        并通过事件机制把相关记忆注入 LLM Agent，使系统具备跨会话个性化和经验积累能力。

它和普通 RAG 的区别是：

能力 Document RAG xtalk-memory
信息来源 用户上传文档 对话、工具调用、偏好、任务状态、失败经验
生命周期 多数是静态文档 动态变化、可更新、可遗忘
结构 chunk + embedding semantic / episodic / procedural / reflective memory
目标 回答文档相关问题 让 Agent 变得更了解用户、更会做事
更新方式 用户上传或重建索引 自动抽取、合并、反思、冲突解决
自进化 弱 强

2. 总体架构设计

建议新增一个独立模块：

src/xtalk/memory/
          __init__.py
          schema.py
          interfaces.py
          store.py
          retriever.py
          extractor.py
          updater.py
          reflector.py
          manager.py
          tools.py
          injector.py

整体架构如下：

User Speech
           ↓
        ASR Final Text
           ↓
        MemoryRetrieveRequest
           ↓
        MemoryManager
           ↓
        MemoryStore.search()
           ↓
        MemoryRetrieved
           ↓
        MemoryContextInjector
           ↓
        LLM Agent Prompt / Tool Context
           ↓
        LLM Response
           ↓
        TTS Output

        同时后台异步：
        ASR Text + LLM Response + Tool Result + Speaker Info
           ↓
        MemoryWriteRequest
           ↓
        MemoryExtractor
           ↓
        MemoryUpdater
           ↓
        MemoryStore.add/update/delete
           ↓
        MemoryUpdated

        会话结束或定时：
        Session Logs
           ↓
        ReflectionManager
           ↓
        Reflection Memory / Policy Suggestion

核心原则是：读取记忆可以参与主链路，但必须有超时；写入记忆和反思必须异步后台执行，不能阻塞 ASR → LLM → TTS 的低延迟链路。

X-Talk 本身就是围绕 EventBus、Manager、Pipeline 的分层架构设计的，论文中也强调所有模块通过中心事件总线异步通信，支持模块解耦、动态协调和低延迟。 所以 memory 模块也应该遵守这个范式，而不是直接塞进 DefaultAgent 里硬耦合。

3. Memory 类型设计

不要把所有记忆都放在一个向量库里。建议至少分成五类。

3.1 Working Memory：当前任务工作记忆

保存当前会话、当前任务、当前 turn 的临时状态。

例如：

当前用户正在配置 X-Talk memory 模块
        当前问题是 memory 如何接入 EventBus
        当前回答需要偏工程实现

生命周期：

session 内有效
        服务关闭或会话结束后可摘要，不一定原样持久化

3.2 Episodic Memory：事件记忆

保存“发生过什么”。

例如：

2026-05-07，用户询问如何给 X-Talk 增加 memory/self-evolving 模块。
        用户曾经上传过 X-Talk 论文并希望基于其架构开发。
        用户曾讨论 Git/GitHub 多人协作范式。

特点：

有时间
        有来源
        可追溯
        适合向量检索

3.3 Semantic Memory：长期事实与偏好

保存比较稳定的用户画像和偏好。

例如：

用户偏好中文技术解释。
        用户正在开发级联式 AI 语音 Agent。
        用户关注 agent memory、self-evolving、X-Talk 架构扩展。
        用户希望回答偏工程落地，而不是纯理论综述。

特点：

稳定
        压缩
        可更新
        适合注入 prompt

3.4 Procedural Memory：技能/流程记忆

保存 Agent 学到的操作流程、工具调用经验、项目开发步骤。

例如：

给 X-Talk 新增模块时，应遵循 interface → pipeline slot → event → manager → service registration。
        添加新工具时，应通过 add_agent_tools 注册 LangChain tool。

X-Talk 文档明确支持通过 add_agent_tools 增加文本工具，工具应为 LangChain tool，内置工具包括 web_search、get_time、emotion、timbre、speed 等。([X-Talk][3]) 这说明 procedural memory 可以和 tool-use 机制自然结合。

3.5 Reflective Memory：反思/自进化记忆

保存系统从历史交互中总结出来的改进经验。

例如：

用户多次要求“设计思路 + 模块拆分 + 数据结构”，以后回答此类问题应优先给架构图和开发路线。
        某类 memory 检索结果经常噪声高，需要提高 semantic memory 权重。
        某个工具调用延迟高，实时语音链路中应先生成缓冲话术。

这是 self-evolving 的核心，但第一版不要让它自动改代码。应该先做：

反思 → 生成策略建议 → 人类确认 → 再进入配置或代码

4. 核心组件设计

4.1 MemoryStore

负责长期持久化。

建议第一版采用：

SQLite：存 metadata、user_id、session_id、type、confidence、timestamps
        Chroma / FAISS：存 embedding 向量
        JSONL：存 debug / audit log

接口：

class MemoryStore:
            async def add(self, item: "MemoryItem") -> str:
                ...

            async def search(
                self,
                query: str,
                user_id: str,
                memory_types: list[str] | None = None,
                limit: int = 5,
                filters: dict | None = None,
            ) -> list["MemoryItem"]:
                ...

            async def update(self, memory_id: str, patch: dict) -> None:
                ...

            async def delete(self, memory_id: str) -> None:
                ...

            async def forget_user(self, user_id: str) -> None:
                ...

            async def close(self) -> None:
                ...

第一版不建议直接上复杂图数据库。更稳妥路线是：

Phase 1：SQLite + Vector DB
        Phase 2：增加 relation table
        Phase 3：升级 temporal graph memory

4.2 MemoryItem Schema

建议每条记忆都必须结构化，而不是只存一句话。

@dataclass
        class MemoryItem:
            id: str
            user_id: str
            session_id: str | None
            speaker_id: str | None

            type: Literal[
                "working",
                "episodic",
                "semantic",
                "procedural",
                "reflective",
            ]

            content: str
            embedding_text: str

            source: Literal[
                "conversation",
                "tool_result",
                "user_explicit",
                "reflection",
                "document",
            ]

            confidence: float
            importance: float

            created_at: float
            updated_at: float
            last_accessed_at: float | None
            expires_at: float | None

            evidence: list[str]
            metadata: dict

关键字段解释：

confidence：这条记忆是否可信
        importance：是否值得长期保留
        expires_at：是否会过期
        evidence：这条记忆来自哪几句话或哪次工具调用
        metadata：可放 turn_id、emotion、speaker、retrieval score 等

4.3 MemoryExtractor

负责从对话中抽取候选记忆。

输入：

user_text
        assistant_text
        tool_results
        speaker_id
        session_id
        existing_memories

输出：

[
          {
            "type": "semantic",
            "content": "用户正在开发 X-Talk 的 memory/self-evolving 模块。",
            "confidence": 0.93,
            "importance": 0.87,
            "source": "conversation",
            "should_write": true
          }
        ]

它需要做三件事：

1. 判断是否值得记忆
        2. 抽取成结构化 memory item
        3. 标注类型、置信度、重要性和证据

强烈建议第一版设置写入门槛：

confidence >= 0.75
        importance >= 0.60
        不包含敏感隐私
        不是短期闲聊
        不是模型自己臆测

4.4 MemoryUpdater

负责去重、合并、冲突和遗忘。

典型逻辑：

新记忆进入
           ↓
        搜索相似旧记忆
           ↓
        如果重复：更新 last_seen / confidence
           ↓
        如果补充：合并内容
           ↓
        如果冲突：保留版本，标记 conflict
           ↓
        如果过期：降权或删除

例如：

旧记忆：用户喜欢英文回答
        新记忆：用户希望之后用中文解释技术问题

不要简单覆盖，而是记录：

{
          "old": "用户喜欢英文回答",
          "new": "用户希望之后用中文解释技术问题",
          "relation": "conflict",
          "resolution": "prefer_recent_explicit_preference"
        }

4.5 MemoryRetriever

负责检索。

不要只做向量相似度。建议第一版用混合排序：

score =
          0.45 * embedding_similarity
        + 0.20 * recency_score
        + 0.15 * importance
        + 0.10 * confidence
        + 0.10 * user_or_speaker_match

检索流程：

当前用户输入
           ↓
        query rewrite
           ↓
        semantic search
           ↓
        metadata filter
           ↓
        rerank
           ↓
        top-k memory
           ↓
        prompt injection

每轮最多注入少量记忆：

semantic memory：3～5 条
        episodic memory：1～3 条
        procedural memory：0～2 条
        reflective memory：0～2 条

4.6 MemoryContextInjector

负责把记忆转成 Agent 能用的上下文。

示例注入格式：

Relevant long-term memory:
        - 用户正在开发 X-Talk 的 memory/self-evolving 模块。
        - 用户偏好中文、结构化、工程落地的解释。
        - 给 X-Talk 新增能力时应遵循 EventBus + Manager + Pipeline 的扩展范式。

        Use these memories only when relevant. Do not mention them unless helpful.

注意：不要把所有记忆都塞进 prompt。Memory 的价值在于“少而准”。

4.7 MemoryManager

MemoryManager 是 xtalk-memory 的核心。它应该作为 X-Talk Manager 注册进 Service。

X-Talk 文档中给出的自定义扩展路径是：先定义新模型或 Pipeline slot，然后通过 EventBus 加新的 Manager 订阅已有 Event，也可以创建新 Event。([X-Talk][4]) 这正好适合 MemoryManager。

MemoryManager 负责：

订阅 ASR final event
        订阅 LLM response finish event
        订阅 tool result event
        订阅 speaker event
        发布 MemoryRetrieved
        发布 MemoryUpdated
        管理后台 memory write task
        管理 session shutdown 时的 summary / reflection

6. 和 X-Talk Pipeline 的集成

X-Talk 自定义 Pipeline 文档提到，如果要新增 Pipeline 功能，需要把新 slot 注册为 dataclass field，并指定 clone 行为；如果 slot 没有进入 additional_model_registry，config 加载路径不会自动填充它。([X-Talk][4])

建议新增：

@dataclass(init=False)
        class MemoryPipeline(DefaultPipeline):
            memory_store: Optional[MemoryStore] = field(
                default=None,
                metadata={"init_key": "memory_store", "clone": False},
            )

            memory_extractor: Optional[MemoryExtractor] = field(
                default=None,
                metadata={"init_key": "memory_extractor", "clone": True},
            )

            memory_retriever: Optional[MemoryRetriever] = field(
                default=None,
                metadata={"init_key": "memory_retriever", "clone": True},
            )

            memory_reflector: Optional[MemoryReflector] = field(
                default=None,
                metadata={"init_key": "memory_reflector", "clone": True},
            )

clone 原则：

memory_store:
          如果是数据库连接池 / Chroma client，可 clone=False
          如果内部维护 session cache，则 clone=True

        memory_extractor:
          如果有 per-session prompt state，clone=True

        memory_retriever:
          如果只读无状态，可 clone=False
          如果有 turn-level cache，clone=True

        memory_reflector:
          一般 clone=True，因为它会积累 session-level 交互轨迹

这和 X-Talk 论文中的状态隔离原则一致：模型参数可以共享，但 streaming buffer、intermediate queue 等可变状态需要按 session 隔离。

7. Agent Tools 设计

Memory 不应该只靠后台自动抽取，也应该暴露给 LLM Agent 主动调用。

建议新增三个工具：

recall_memory
        remember_memory
        forget_memory

recall_memory

@tool
        async def recall_memory(query: str, limit: int = 5) -> str:
            """Retrieve relevant long-term memories for the current user."""

使用场景：

用户问：我之前说过我要给 X-Talk 加什么模块？
        Agent 调用 recall_memory("X-Talk module plan")

remember_memory

@tool
        async def remember_memory(content: str, memory_type: str = "semantic") -> str:
            """Store an explicit user-approved memory."""

使用场景：

用户说：记住，我现在主要想做 X-Talk memory 模块。
        Agent 调用 remember_memory(...)

forget_memory

@tool
        async def forget_memory(query: str) -> str:
            """Forget memories matching the user's request."""

使用场景：

用户说：忘掉我刚才说的 API key。
        Agent 调用 forget_memory(...)

注意：remember_memory 和 forget_memory 必须优先处理用户显式意图。自动记忆只能作为后台优化，不能覆盖用户控制权。

8. 自进化机制设计

xtalk-memory 的 self-evolving 可以分三层做。

第一层：Memory Evolution

系统自动维护记忆质量。

候选记忆
           ↓
        去重
           ↓
        合并
           ↓
        冲突解决
           ↓
        重要性更新
           ↓
        过期遗忘

例如：

用户多次要求“请给出工程实现”
           ↓
        更新 semantic memory：
        “用户偏好工程落地型回答”

第二层：Policy Evolution

系统根据记忆调整交互策略。

例如：

如果用户偏好简洁：
          回答更短

        如果用户偏好代码：
          回答中优先给 interface / class / event

        如果某工具经常超时：
          降低该工具优先级，先给缓冲话术

可以把策略记成 reflective memory：

{
          "type": "reflective",
          "content": "在 X-Talk 架构设计问题中，用户更需要模块边界、事件流和开发路线，而不是泛泛综述。",
          "confidence": 0.88
        }

第三层：System Evolution

系统生成可审查的改进建议。

ReflectionManager
           ↓
        分析历史失败案例
           ↓
        生成 evolution report
           ↓
        开发者确认
           ↓
        进入 issue / config / PR

例如：

建议：
        - 为 MemoryManager 增加 300ms retrieval timeout
        - 为 MemoryExtractor 增加敏感信息过滤
        - 为 recall_memory tool 增加 user_id filter

不要第一版就做：

自动修改源码
        自动改生产配置
        自动 merge PR

这样风险太高。更合理的是 human-in-the-loop self-evolution。

9. 存储目录设计

因为 X-Talk 当前 session embedding 会在 shutdown 时删除，长期 memory 应该单独放。

建议：

data/
          memory/
            users/
              <user_id>/
                profile.json
                semantic.sqlite
                episodic.sqlite
                procedural.sqlite
                reflective.sqlite
                vector_index/
                  chroma/
                audit.jsonl
            global/
              skills/
              policies/

区分：

session memory:
          data/sessions/<session_id>/...

        long-term memory:
          data/memory/users/<user_id>/...

不要把长期记忆写入 session 目录。

11. 低延迟设计原则

X-Talk 的主要价值是实时语音交互，所以 memory 不能拖慢系统。

建议设置：

Memory retrieval timeout：200～500ms
        Memory write：后台异步
        Memory reflection：session end 或低峰后台执行
        Memory rerank：只对 top-20 做
        Prompt injection：限制 token 数

实时链路：

ASR → Memory Retrieval → LLM → TTS

其中 retrieval 只能短暂参与：

如果 300ms 内检索完成：
          注入 memory

        如果超时：
          跳过 memory，直接生成

伪代码：

try:
            memories = await asyncio.wait_for(
                memory_store.search(query, user_id=user_id, limit=5),
                timeout=0.3,
            )
        except TimeoutError:
            memories = []

写入链路：

asyncio.create_task(
            memory_manager.extract_and_write(turn_context)
        )

12. 隐私与安全原则

Memory 模块必须从第一版就考虑安全。

至少要支持：

1. 用户显式关闭 memory
        2. 用户查看 memory
        3. 用户删除某条 memory
        4. 用户删除全部 memory
        5. 敏感信息默认不自动存储
        6. user_id / speaker_id / session_id 严格隔离
        7. audit log 记录每次写入原因

敏感信息过滤：

API key
        密码
        身份证
        银行卡
        详细地址
        医疗诊断
        政治 / 宗教 / 敏感身份

自动写入策略：

普通偏好：可自动写入
        长期任务目标：可自动写入
        敏感个人信息：需要用户确认
        凭证类信息：禁止写入

        MemoryContextInjector

验收标准：

第一轮：用户说“记住我正在开发 xtalk-memory”
        第二轮：用户问“我刚才说我在开发什么？”
        系统能回答
        重启服务后仍能回答
        用户说“忘掉这件事”后不能再回答

Phase 2：自动抽取

目标：

不需要用户每次说“记住”，系统能自动抽取有价值记忆

实现：

MemoryExtractor
        MemoryWritePolicy
        MemoryUpdater
        重复合并
        置信度管理

验收标准：

用户多次表达偏好后，系统能形成 semantic memory
        无意义闲聊不会写入
        敏感信息不会自动写入

Phase 3：反思式自进化

目标：

系统能总结交互经验，形成 reflective memory

实现：

MemoryReflector
        SessionSummary
        FailureCaseLogger
        EvolutionReport

验收标准：

系统能生成：
        - 用户偏好总结
        - 工具调用失败总结
        - 回答策略建议
        - 可供开发者审查的改进报告

Phase 4：图记忆

目标：

支持实体、事件、时间、关系和冲突更新

实现：

Entity table
        Relation table
        Temporal event table
        Hybrid vector + graph retrieval

适合后续研究创新。

# src/xtalk/memory/tools.py

        from langchain.tools import tool


        def build_memory_tools(memory_store, user_id_getter):
            @tool
            async def recall_memory(query: str, limit: int = 5) -> str:
                """Retrieve relevant long-term memories for the current user."""
                user_id = user_id_getter()
                memories = await memory_store.search(query=query, user_id=user_id, limit=limit)
                if not memories:
                    return "No relevant memory found."
                return "\n".join(f"- {m.content}" for m in memories)

            @tool
            async def remember_memory(content: str, memory_type: str = "semantic") -> str:
                """Store an explicit user-approved memory."""
                user_id = user_id_getter()
                item = MemoryItem(
                    user_id=user_id,
                    content=content,
                    type=memory_type,
                    source="user_explicit",
                    confidence=1.0,
                    importance=0.9,
                )
                memory_id = await memory_store.add(item)
                return f"Memory saved: {memory_id}"

            @tool
            async def forget_memory(query: str) -> str:
                """Forget memories matching the user's request."""
                user_id = user_id_getter()
                memories = await memory_store.search(query=query, user_id=user_id, limit=10)
                for memory in memories:
                    await memory_store.delete(memory.id)
                return f"Forgot {len(memories)} matching memories."

            return [recall_memory, remember_memory, forget_memory]

16. 最推荐的最终形态

我建议你把 xtalk-memory 做成下面这个结构：

xtalk-memory
        ├── MemoryStore
        │   ├── SQLite metadata
        │   ├── Vector index
        │   └── Audit log
        │
        ├── MemoryManager
        │   ├── subscribe ASR / LLM / Tool / Speaker events
        │   ├── publish MemoryRetrieved / MemoryUpdated
        │   └── async write / reflection
        │
        ├── MemoryExtractor
        │   ├── salience detection
        │   ├── preference extraction
        │   ├── fact extraction
        │   └── privacy filter
        │
        ├── MemoryUpdater
        │   ├── dedup
        │   ├── merge
        │   ├── conflict resolution
        │   └── forgetting
        │
        ├── MemoryRetriever
        │   ├── vector search
        │   ├── recency / confidence / importance rerank
        │   └── top-k selection
        │
        ├── MemoryTools
        │   ├── recall_memory
        │   ├── remember_memory
        │   └── forget_memory
        │
        └── MemoryReflector
            ├── session summary
            ├── failure analysis
            ├── policy suggestion
            └── evolution report

一句话设计原则：

xtalk-memory 应该是 X-Talk 的长期认知层：
        以 EventBus 接入，以 Manager 运转，以 Store 持久化，以 Tool 暴露给 Agent，
        以 Extractor/Updater/Reflector 实现记忆演化，
        同时严格保证低延迟、用户隔离、可遗忘和可审计。

第一版先做 Long-term Memory MVP，不要急着做完整 self-evolving。等“跨会话记忆 + 主动记忆工具 + 自动抽取 + 遗忘机制”跑通后，再加入 reflection 和 temporal graph memory，这样最稳。
